## Decision 2: a pending project settings change is withdrawn when the machine loses the project

- **Where.** `claim-service.ts` → `bindScope()` is the one place a project changes owner. It is used by an
  approved takeover (`decideClaimRequest`), the owner's reassignment (`ownerAssign`), a release (`release`) and a
  revocation (`releaseEverything`). For a project scope it now calls the new
  `project-change-service.ts` → `withdrawProjectChanges(tx, projectId, to)` in the same transaction, with the
  project row already locked (the same lock order as `decideProjectChange`).
- **Effect.** Pending `project_change_requests` of that project from any machine other than the new holder become
  `withdrawn`, with `decided_at` set. For each one, a `project.change_decided {requestId, projectId, machineId,
  status: 'withdrawn'}` event is appended, targeted at the requesting machine. The owner stream receives every
  event, so the web inbox's pending list refreshes through the existing `invalidationsFor` mapping. The project
  itself is not changed. A rejected takeover does not move the project, so nothing is withdrawn.
- **Late decisions.** `decideProjectChange` already refuses a request that is no longer pending, so approving or
  rejecting a withdrawn request returns 409 `CONFLICT` ("the project change request is already withdrawn").
- **Storage.** The migration `apps/api/drizzle/0004_project_change_withdrawn.sql` (generated by drizzle-kit)
  adds `withdrawn` to the enum `project_change_status`.
- **Shared (additive).**
  - `ProjectChangeStatus` gains `withdrawn`, and the `project.change_decided` status gains `withdrawn`.
  - New `ProjectChangeOutcome {requestId, status}`.
  - `DaemonProject.lastChange` is nullable and defaults to null. `ProjectDetail.lastChange` is new.
- **Daemon view.** `GET /v1/daemon/projects` now returns `lastChange`: the calling machine's latest change
  request for each project, whatever its status. It comes from `changesOf()`, a single `DISTINCT ON
  (project_id)` query that replaces `pendingChangesOf()`, and `pendingChange` is derived from it.
- **Desktop.**
  - `projectDetail()` passes `lastChange` through.
  - In Settings → Projects, the panel still re-reads the project every 5 s while a request is pending. Once the
    request is no longer pending, it shows the text for `lastChange.status` of the request it was waiting on.
    A withdrawn request shows "Yêu cầu đổi đã tự rút vì máy này không còn giữ project; loại project giữ
    nguyên."
  - This replaces the old guess, which compared the asked values with the current ones. That guess would have
    shown "đã từ chối" for a withdrawn request.
- **Daemon and web.** No code change was needed. The daemon already turns `project.change_decided` into a
  project refresh, and the web inbox lists only pending requests.

### Tests

- API, `test/project-changes.test.ts`, new describe block with 5 tests. Each withdrawal path checks:
  - the row is `withdrawn` with a `decided_at`;
  - exactly one `project.change_decided` event, targeted at the requesting machine, with status `withdrawn`;
  - the project is unchanged;
  - the owner list shows `withdrawn`, and the pending list is empty;
  - both approve and reject then return 409, and the project is still unchanged.

  | Case | Result |
  |---|---|
  | Approved takeover | Withdrawn. While the takeover request is only pending, the change stays pending. Afterwards `lastChange` is `withdrawn` for the old machine and null for the new one, and the new holder can file its own request. |
  | Owner reassignment | Withdrawn. |
  | Rejected takeover | Stays pending, and no event is sent. |
  | Release | Withdrawn, and the machine's view shows `ownerState: unowned` and `lastChange: withdrawn`. |
  | Machine revocation | Withdrawn. |
- Desktop host test (`host-service.test.ts`), run against the real API:
  - after the owner approves, `lastChange` is `approved`;
  - a second request shows `lastChange: pending`;
  - releasing the project turns it into `withdrawn`.
- Electron E2E (`test/e2e/project-settings.spec.ts`), new test:
  1. The app asks for a type change through the UI and shows "Đang chờ chủ dự án xác nhận".
  2. A second machine pairs, and the owner reassigns the project to it.
  3. The pending text disappears, and "Yêu cầu đổi đã tự rút" is shown.
  4. The type select is back on `backend`, and the owner's pending list no longer has the request.

  `prepare-db.ts` now makes 8 pairing codes instead of 6, and the new test uses codes 5 and 6.

## Decision 3: a zip per architecture

- `apps/desktop/electron-builder.yml`:
  - `mac.target` is now `dmg` and `zip`, each with `arch: [arm64, x64]`;
  - the zip name comes from `mac.artifactName: 2P-Crew-${version}-${arch}-mac.${ext}`. electron-builder has no
    top-level `zip` section, and the dmg keeps its own `dmg.artifactName`;
  - electron-updater picks the arm64 file by the `arm64` in its name.
- `scripts/package-mac.mjs`:
  - builds the `['dmg', 'zip']` targets for both architectures in one electron-builder run, from the same
    staging folder;
  - the `afterPack` hook `keepOnlyArch()` runs once per architecture, before signing and before either
    artifact is made from that app. So the zips are stripped exactly like the dmgs.
- `test/main-logic.test.ts` checks:
  - the target list;
  - that the dmg name still matches `dmgAssetName()`;
  - the zip names `2P-Crew-<v>-arm64-mac.zip` and `2P-Crew-<v>-x64-mac.zip`.
- CI (`.github/workflows/ci.yml`, release job):
  - `package:mac --publish` already uploads every artifact electron-builder makes (dmg, zip, blockmap,
    `latest-mac.yml`), so only comments and names changed;
  - the workflow artifact is renamed from `dmgs` to `mac-release` and now keeps `*.dmg`, `*.zip` and
    `latest-mac.yml`.
- The signing notes in `docs/flows/desktop-app.md` no longer say that a zip target must be added when signing is
  turned on.

## Notes and things left undone

- The desktop learns of a withdrawal from the project view, not from a push to the renderer. The daemon
  receives the targeted `project.change_decided` event and refreshes. The renderer re-reads
  `projects.detail` every 5 s while a request is pending, so the withdrawn text appears within about 5 s. There
  is no daemon-to-renderer event channel for project changes. Adding one was not needed for this behaviour.
- A revoked machine cannot read the API any more. In that case the panel shows "Chưa đọc được project từ
  server" instead of the withdrawn text. The server side is still withdrawn and tested.
- Requests that were already pending before this change, from machines that had already lost the project, are
  not cleaned up. That is only possible for rows created before this migration; none are known.
- `plans/260928-0613-crew-platform/plan.md` has uncommitted changes (Session 16) that are not mine. They were
  left out of the gate check index.
