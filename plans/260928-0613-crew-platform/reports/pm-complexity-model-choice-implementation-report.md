# PM rates complexity to choose the dev and QC model (Validation Session 17): Implementation Report

Date: 2026-09-29 · Status: done · Branch: `main`, uncommitted (as asked) · Scope: `apps/api`, `apps/daemon`,
`apps/web` (Details display and E2E), `packages/shared` (additive), `docs/`, `phase-07-agent-workflow.md`.

The PM now has to rate every dev and QC subtask with `complexity` and a one-line `complexityReason`, and the run's
model comes only from that rating. There is no dev or QC model default left in the daemon. The full suite, lint,
build and the web E2E pass. The commit gate passes on a temporary index built from HEAD plus this change, with no
trailer.

## 1. The rating is required at creation

- **Schema (shared, additive).** `CreateSubtaskRequest` gains `complexityReason` (trimmed, 1 to 500 characters).
  A `superRefine` requires both `complexity` and `complexityReason` when `type` is `dev` or `qc`. `pm_task` and
  `docs_init` are unchanged. `Ticket` gains `complexityReason: string | null`.
- **API answer.** A dev or QC subtask without them gets 400 `VALIDATION_FAILED`. The `details` list names the
  missing field and says why in Vietnamese, for example "Subtask dev bắt buộc có complexity (trivial | small |
  medium | large): PM đánh giá độ phức tạp để chọn model, không có model mặc định cho dev và QC." The daemon's
  `errorText()` already passes `details` to the agent, so the PM reads that message in the tool result.
- **Agent tool.** `create_subtask` now declares `complexity` and `complexityReason` as required inputs, with
  Vietnamese descriptions. `model` is described as a deliberate override whose reason goes in `complexityReason`.
- **Storage.** The migration `apps/api/drizzle/0006_pm_complexity_reason.sql` (generated by drizzle-kit) adds the
  nullable column `tickets.complexity_reason`. The DTO returns it.
- **Web.** In the ticket Details box, the "Độ phức tạp" item shows `Lý do: <reason>` under the rating. The web
  E2E checks this at all three viewports; on the phone it opens the collapsed Details first.

## 2. Model choice without defaults

- **`model-policy.ts`.** `STAGE_DEFAULTS` now covers only the assistant and PM stages. For the `dev` stage (dev
  and bug tickets) and the `qc` stage, the model and effort come from `config.models.complexityMap[complexity]`,
  and then the allowlist clamp, which is unchanged. A `model` or `effort` the PM set on the subtask still wins, as
  a deliberate override. It can only exist next to a rating and its reason, because the server requires both.
- **Unrated legacy ticket.** A dev, bug or QC ticket without `complexity` throws `MissingComplexityError`, even
  when it has a model. The error goes through the job runner's existing crash path (`launch` → `reportCrash`):
  the job is `failed`, the ticket gets a comment and is `blocked`, and no agent runs. The comment asks the PM to
  rate it: "Ticket này chưa được PM đánh giá độ phức tạp (complexity) nên không chọn được model cho lượt dev:
  không có model mặc định cho dev và QC. PM cần đánh giá lại: tạo subtask thay thế có complexity (...) và
  complexityReason (một dòng lý do), rồi nhờ chủ dự án huỷ ticket này."
- **Runtime default planner.** `chooseModel()` in `job-runner.ts` is used by tests and exported from the
  library. It lost its dev and QC defaults the same way, so no code path still picks a dev or QC model silently.
- **Unchanged.** Docs-init and docs-update stay fixed on sonnet/high. The assistant stays on haiku, and the PM on
  sonnet, or opus when the pm_task is `large`.

## 3. PM prompt

- **`pm-analyze.md`, breakdown step.** It now says:
  - `complexity` and `complexityReason` are required, there is no default model, and the server refuses a
    subtask without them;
  - rate dev on implementation effort (files and modules touched, new logic, migrations, regression risk);
  - rate QC **separately** on its own testing effort: UI testing through Playwright or Maestro, the number of flows
    and acceptance criteria, risk and security sensitivity. Do not copy the dev rating;
  - worked examples (dev `small`, QC `medium` for three UI flows, QC `large` for a security-sensitive login flow);
  - set `model`/`effort` only as a deliberate override with the reason, and `fable` only with a written reason
    that whole-repo context is needed.
- **`pm-accept.md`.** A conflict-resolution dev and QC pair needs its own ratings. `reject_work` explains what the
  bug and the retest inherit.
- **`qc.md`.** `file_bug` explains what the bug and the retest inherit.

## 4. A bug runs on the PM's rating of its dev ticket

- **`fileBug()`** (QC `file_bug` and PM `reject_work`). The bug now takes `complexity`, `model` and `effort` from
  the **origin dev ticket** (`originDevId`, else the ticket under test). Before, it took them from the ticket
  under test, which for a later cycle was the previous bug. Its reason is `kế thừa từ <DEV-KEY>: <dev reason>`.
- **Retest.** The QC retest keeps the QC template's rating (the filing QC, or the rejected ticket's own QC), with
  the reason `kế thừa từ <QC-KEY>: …`. A reason that already carries the prefix is copied as is, so later cycles
  do not nest it.
- **Bug-cycle cap.** The cap message now uses the same origin row, which replaced a second lookup.

## 5. Tests

- **`model-policy.test.ts`.** The map is applied for dev and QC, and the machine's own map is used. A subtask
  model or effort overrides it. Dev and QC throw `MissingComplexityError` without a rating, for every model
  including none. Fable is clamped unless it is allowed. The docs, assistant and PM cases are unchanged.
- **API.**
  - `machine-scope.test.ts`, through the real route: a missing rating, a missing reason or a blank reason each
    return 400, with Vietnamese messages in `details`, for dev and QC. A rated dev with a model override and a
    rated QC are created with the reason stored. A docs-init subtask needs no rating.
  - `bug-loop.test.ts`: a dev rated `large` (opus/xhigh) and its QC rated `small`. The bug inherits the dev rating
    and reason, the retest inherits the QC's, a second cycle does not nest the prefix, and a PM rejection of the
    bug fix inherits from the origin dev.
  - Every other test that creates dev or QC subtasks now passes a rating, through the `RATED` helper in
    `test/helpers/test-db.ts`.
- **Daemon.**
  - `daemon.test.ts`: a legacy dev ticket, with its rating cleared in the database (new `clearRating` helper), runs
    through the real `rolePlanner`. The job fails, the ticket is blocked with the Vietnamese comment, and no agent
    runs.
  - Lifecycle: the `pm_analyze` macro now requires `complexity` and `qcComplexity` for each subtask (with optional
    `reason` and `qcReason`), and all 15 fixtures name both.
  - New scenario `16-qc-own-rating.yaml`. Dev is rated `large` and runs on opus/high. QC is rated `trivial` and runs
    on haiku/low. The bug QC files runs on opus with the reason `kế thừa từ <DEV-KEY>: …`, and the retest runs on
    haiku.
  - `no-docs-init-first` looked up "Trang sản phẩm" without a type. Three tickets have that title, and the row
    order changed once the fixture changed, so the check picked the request. It now asks for the `dev` ticket.
- **Web E2E.** The seeded dev and QC subtasks carry ratings, and core-flows checks the reason in Details.

## Notes and open questions

- **Remedy for an unrated legacy ticket.** The PM has no tool to change an existing subtask's rating, and an
  agent cannot cancel a ticket. The comment therefore tells the PM to create a rated replacement and ask the
  owner to cancel the old ticket. A small `rate_subtask` tool (PM only, dev or QC in the PM's tree) would let the
  PM rate in place instead. It was not added because it is outside the requested scope.
- **Fable rule.** The server enforces that every dev and QC subtask has a reason, override or not. That the
  reason actually justifies Fable stays a prompt rule, as before. The server does not parse the reason.
