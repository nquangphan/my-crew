## Important — chặn triển khai

1. **Heartbeat qua reboot chưa có thứ tự boot và replay bền vững.** Plan dòng **51, 57, 64, 112** dùng `(machine_id,boot_id,sequence)` và chỉ lưu một hàng heartbeat cuối (`boot_id,sequence,body_hash`). Sau khi boot B được chấp nhận, gói trễ từ boot A với sequence lớn hơn có thể bị coi là boot mới và ghi đè trạng thái; UUID boot không có thứ tự. Ngay trong cùng boot, một heartbeat hợp lệ cũ bị retry sau heartbeat mới cũng không thể replay theo lời hứa “duplicate same body replays” vì DB chỉ giữ hash cuối. **Sửa:** định nghĩa handshake/CAS cho boot generation dưới machine lock, một boot hiện hành và danh sách boot cũ bị từ chối; lưu receipt/idempotency cho các `(boot,sequence)` còn trong cửa sổ retry hoặc giới hạn rõ replay chỉ với latest và điều chỉnh test. Thêm test A→B→gói trễ A, B sequence reset, duplicate cũ sau sequence mới, và server restart. Heartbeat không được tự suy diễn process chết hay thả guard (spec dòng 179–181; Phase 02 dòng 488).

2. **Đường ghi `applied` chưa có hợp đồng, nên hash/revision có thể báo sai.** Plan dòng **51, 53–64, 124, 151** nói applied chỉ tăng sau hai pin được xác minh, nhưng danh sách route không có mutation báo kết quả cài đặt; `heartbeat` vừa mang inventory vừa mang `appliedConfigRevision`, trong khi `gateway_applied` chỉ có revision/inventory. Không rõ server lấy revision từ đâu, có so từng `payloadSha256/treeSha256/manifestSha256` với đúng desired revision trong *cùng transaction* hay không, và UI lấy trạng thái từng bộ đang cài/lỗi ở đâu. **Sửa:** đóng băng một report/ACK contract rõ ràng (route riêng hoặc heartbeat có luật atomically apply) gồm revision được thử, kết quả từng bundle, hash đã đo, lỗi và thời điểm; CAS với current desired revision, chỉ advance applied khi cả hai khớp exact pin, giữ applied cũ khi lỗi/desired đổi. Thêm test host báo revision đúng nhưng hash sai, partial install, report cũ đến sau config mới, crash/retry report. Spec dòng 106–114 đòi phân biệt desired/installed từng bộ.

3. **`reserve → crash → not_started` là suy luận không an toàn.** Plan dòng **66, 89–91, 105, 152, 165** chỉ fsync `reserve` trước spawn và `markSpawned` sau spawn. Host có thể crash đúng sau OS spawn nhưng trước `markSpawned`; journal giống hệt trường hợp chưa spawn, trong khi child vẫn chạy. Sau claim thành công nhưng trước spawn, Phase 02 chỉ nhận `reconcile(stopped)` với provenance dừng tiến trình thực (`phase-02-server-docs.md` dòng 488); không có API “never started” để giải phóng guard. **Sửa:** pin giao thức launcher có handshake/fence bền vững trước khi child được phép làm side effect, lưu PID + start identity/process group trước khi release; nếu không chứng minh được không-start, ghi `unknown`, giữ guard và escalation. Với claim thật sự chưa spawn, xác định đường terminal hợp lệ được Phase 02 chấp nhận hoặc ghi dependency cần re-review hợp đồng đóng băng; tuyệt đối không giả stop proof. Test kill host tại từng điểm reserve/claim/spawn/markSpawned và xác nhận child/guard không nhân đôi.

4. **ACK/retry sync mâu thuẫn với lệnh đã `completed`.** Plan dòng **60–64, 151, 165** yêu cầu một bundle lỗi thì retry *cùng command* và ACK trả cùng kết quả, nhưng completion ACK khác `result` phải 409; nếu ACK `completed` với lỗi thì cùng command không thể hoàn tất thành công sau retry. Luật cho ACK `received` đến muộn sau `completed` cũng chưa xác định. **Sửa:** chọn một state machine: giữ command ở `received` và retry side effect với cùng command ID cho tới khi cả hai pin khớp, rồi ACK `completed`; hoặc complete failure và server phát command mới với ID mới cùng config revision. Quy định ACK `received` trễ chỉ replay/no-op, không hạ state hay xóa completion; ghi rõ trạng thái partial và backoff/retry. Test crash sau install nhưng trước ACK, duplicate/out-of-order ACK, lỗi rồi thành công, và config đổi giữa các lần thử.

5. **Idempotency key sau restart chưa gắn với journal side effect.** Plan dòng **33, 61, 152, 165** đòi Phase 02 mutation wrapper dùng `Idempotency-Key`, nhưng host journal chỉ nói lưu cursor/ACK intent và key `(machineId,commandId)`. Claim/result/finalize và gateway ACK là nhiều mutation khác nhau; tái gửi với key mới hoặc dùng lại một key cho phase/body khác có thể tạo event trùng hay conflict. Phase 02 dòng 148 còn yêu cầu `finalize` có key mới. **Sửa:** ghi durable operation record cho từng HTTP mutation gồm route, canonical body hash, idempotency key, response/result và phase; fsync trước network write, replay *đúng* key/body khi không biết kết quả, dùng key riêng khi chuyển phase, đối chiếu server state trước side effect tiếp theo. Test mất reply tại từng mutation và restart giữa receipt/ACK/result/finalize.

6. **Cách ly nguồn được hứa vượt quá thứ có thể chứng minh ở Phase 03.** Plan dòng **170, 173–186, 192, 209–212** đúng khi ghi native Read/child/MCP chưa được chứng nhận và phase04 mới có adapter/real attempt, nhưng Task 6 GREEN lại yêu cầu mọi `Skill`, slash command, direct Read/Bash và child dispatch bị chặn trước action; Task 7 khẳng định “chỉ chosen path trong process inventory”. Inventory, hook giả và `codex sandbox -P` chỉ chứng minh bề mặt riêng, không chứng minh native runtime/child. Báo cáo khảo sát dòng 68–76, 126–138, 169–174 đã nêu giới hạn này. **Sửa:** định nghĩa Phase 03 deliverable là workspace/policy/preflight + bằng chứng no-model, với `ok:false/UNVERIFIED` cho mọi surface chưa thử end-to-end; chuyển PASS native Read/child/skill invoke vào gate Phase 04. Task 7 chỉ assert inventory chính xác và adapter vẫn disabled, không ghi nhận complete isolation. Ghi rõ process-wide enforcement hoặc stronger boundary phải được chứng minh trước dispatch thật; `HOME` riêng và path inventory không phải boundary.

7. **Registry không chứng minh revision BMAD tương ứng payload cài đặt.** Plan dòng **51, 131, 144** ghim full Git revision BMAD nhưng installer chạy `bmad-method@6.12.0` từ npm; version npm và Git tag SHA là hai provenance khác nhau. `treeSha256` còn phụ thuộc output installer, script/config và layout runtime, nhưng plan chưa đóng băng thuật toán manifest/tree hash hay cách xác minh mapping npm tarball ↔ revision. Vì vậy một `InstalledPin` có thể mang revision đúng trên giấy và cây cài đặt khác. **Sửa:** ghi nguồn, npm integrity + SHA-256 tarball, xác minh mapping từ release/tag đến package bằng manifest được audit; hash deterministic output tree với quy tắc canonical path/mode/symlink/metadata, ghi installer version/options/runtime target, và chỉ publish khi exact `DesiredPin` match. Nếu không chứng minh mapping, lưu riêng `sourceRevision` và `packageIntegrity`, không khẳng định tarball là byte của Git commit. Kiểm tra official URL allowlist ở cả server và host; không tin URL trong owner-provided desired JSON. Báo cáo khảo sát dòng 21–27 đã phân biệt tag, npm và hash.

8. **Cleanup path còn cửa sổ thay thế sau khi kiểm tra ownership.** Plan dòng **67, 89, 103, 105** nói register trước sử dụng nhưng test lại gọi “register only host-created”; `canonical no-follow path` chưa đủ nếu một thư mục trung gian bị đổi symlink/rename giữa check và delete. `runId` và path một mình không chứng minh file vẫn là đối tượng Crew tạo, nhất là sau crash. **Sửa:** định nghĩa hai pha `reserveOwnedPath` → create → attest inode/device/owner/root, dùng private run root quyền hạn chặt và deletion qua directory handle hoặc rename/quarantine an toàn với kiểm tra lại identity; bất kỳ mismatch giữ lại, không recursive delete theo path cũ. Test thay symlink/rename giữa xác minh và cleanup, run B trỏ chung inode/hardlink, crash sau register trước create. Spec dòng 208–213 yêu cầu không xóa owner/run khác.
