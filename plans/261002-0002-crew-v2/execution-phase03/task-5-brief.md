## Global Constraints

- V2 độc lập trong `v2/`; không import app, daemon, role prompt, business schema hoặc DB v1. App local chỉ là cổng/trạng thái; server quản lý cấu hình mong muốn.
- Một owner, một máy/project, macOS only. Máy v1 và credential v1 không được nhập. Không dùng DB production/shared, không restart service của owner, không cài công cụ toàn máy, không gọi model có phí trong phase03.
- Mất heartbeat hoặc hết lease không chứng minh process chết. Một ticket chỉ một guard `active_attempt_id`; `finalizing` vẫn giữ guard đến khi terminal result được kiểm chứng và finalize nguyên tử.
- Cả BMAD và Superpowers **source** phải được cài và kiểm hash; runtime projection được kiểm riêng. Run ghim exact source+chosen projection. Chỉ một workflow/projection được nạp vào một process; trợ lý định tuyến có namespace riêng; agent con phải kế thừa immutable context.
- Telemetry mới trước **mỗi** dispatch implement/review/fix; thiếu hoặc vượt ngưỡng thì chờ. Cleanup chỉ xóa tài nguyên do run sở hữu sau xác nhận process dừng; lỗi cleanup lưu lại để retry.
- Nội dung UI/docs tiếng Việt, identifier/path/key tiếng Anh, thời gian API UTC ISO, giao diện `Asia/Ho_Chi_Minh`. Electron renderer local, `contextIsolation`, sandbox, `nodeIntegration:false`, IPC sender allowlist; [Electron security checklist](https://www.electronjs.org/docs/latest/tutorial/security).
- Không updater/signing/deploy trong phase03 (phase09). Không âm thầm đăng ký LaunchAgent vĩnh viễn khi chạy test/dev; onboarding quyền cho persistent service là thao tác sản phẩm riêng, không phải side effect của build.

### Frozen wire contracts

`Workflow='bmad'|'superpowers'`, `Runtime='claude'|'codex'|'api'`. A **runtime-agnostic** `SourcePin={name:Workflow,version:string,sourceRevision:string,sourceUrl:string,payloadSha256:string,packageIntegrity:string|null,sourceManifestSha256:string,sourceTreeSha256:string}` identifies official source bytes/tree. BMAD npm tarball has separately verified `packageIntegrity` and `payloadSha256`; neither is asserted byte-identical to its Git tag. A projection is `ProjectionPin={runtime:Runtime,sourceTreeSha256:string,manifestSha256:string,treeSha256:string,derivation:{tool:string,version:string,options:string[],layoutSchema:string,policySha256:string}}`; exact `sourceTreeSha256` binds it to one source. Claude/Codex projections contain audited discovery layout and official scripts; API projection contains the official skill/script manifest and an adapter tool policy for phase04's API tool loop, **not** Crew-authored PM/dev/QC role prompts. `DesiredWorkflow={source:SourcePin,projections:{claude:ProjectionPin|null,codex:ProjectionPin|null,api:ProjectionPin|null}}`; `GatewayConfig={revision:number,desired:{bmad:DesiredWorkflow,superpowers:DesiredWorkflow},maxJobs:number,enabled:boolean}`. Slots may be `null` until a runtime-specific derivation is audited, but both workflow **sources** are mandatory. Source and projection can update independently and coexist side by side; a null/failed projection makes only that runtime/workflow combination unavailable. Server and host validate official `sourceUrl` against a fixed repository/registry allowlist and exact version/revision, including redirects. Version alone never establishes match.

The frozen domain `Pin={workflow,version,revision,checksum}` is **unchanged**: `toDomainPin(source)={workflow:source.name,version:source.version,revision:source.sourceRevision,checksum:source.sourceTreeSha256}`. Phase02 `tickets.workflow_pin` and `attempts.workflow_pin` carry this source pin. Phase03 companion `AttemptProjectionPin={attemptId:Id,fence:string,processInstanceId:Id,sourceTreeSha256:string,runtime:Runtime,projectionManifestSha256:string,projectionTreeSha256:string,installReportId:Id}` is immutable in migration007 and host journal.

**Selection authority for a fresh attempt:** Phase06 persists `DispatchSelection={runtime:Runtime,sourceTreeSha256:string,projectionManifestSha256:string,projectionTreeSha256:string,installReportId:Id,configRevision:number,decisionId:Id}` in both `commands.payload.selection` and the referenced `decisions.scope.selection` **before** claim; both copies must match exactly. The frozen Phase02 `DispatchPermit` remains `{commandId,ticketId,machineId,bindingRevision,ticketRevision,workflow,checkedAt,expiresAt,telemetryId,decisionId}`. Phase06's `authorizeDispatch(tx,actor,permit)` loads the stored command and decision by IDs under the claim transaction, validates selection against current enabled/runtime availability, current applied config/report and matching source `Pin`, and rejects disabled/old projection or stale config before attempt creation. Phase03 does not implement this production authorizer; default `DISPATCH_NOT_CONFIGURED` remains. No client-supplied selection, boolean or historical report alone grants a fresh claim.

`GatewayProjectionPolicy.authorize(tx,{attemptId,actor}):Promise<DispatchSelection>` is a separate **fail-closed** phase03 companion hook, default `SELECTION_NOT_CONFIGURED` 503 until Phase06 supplies it. It reads `attempt.command_id`, that server-stored command payload and dispatch decision scope, confirms matching decision ID, exact selection, matching attempt machine/fence/process/source `Pin`, and proof that Phase02 claim succeeded under the Phase06 authorizer. Route order under attempt lock: authenticate/check exact actor+fence+process; if an immutable companion row already exists, identical request replays it without mutation and a different pair 409; otherwise call `GatewayProjectionPolicy` and compare request hashes/report ID to returned **server** selection. Client cannot choose a projection. For a **new** row, selection must have been current/enabled at claim and report fully applied; config change after authorized claim does not erase that attempt's selection. A historical report from another attempt is never authority for a fresh attempt. Tests inject a private policy that reads fixture command/decision/current-config rows and enforces these same comparisons; no permissive test boolean. Claim/release requires exact source domain pin and chosen projection companion; run retains that pair until terminal/cleanup. Phase04 adapter consumes the pair and may enable only a certified runtime.

`BundleState='missing'|'installing'|'current'|'mismatch'|'error'`; `SlotStatus<T>={state:BundleState,installed:T|null,lastError:{code:string,message:string}|null,observedAt:string|null}`. `WorkflowStatus={source:SlotStatus<SourcePin>,projections:{claude:SlotStatus<ProjectionPin>,codex:SlotStatus<ProjectionPin>,api:SlotStatus<ProjectionPin>}}`. Public `GatewayStatus` and server status expose one `WorkflowStatus` per workflow; `lastError` is sanitized, never contains path/credential. `gateway_applied.revision` advances only when both source pins and **every non-null desired projection** match exactly; null projections stay unavailable and cannot be selected. A partial result preserves previous applied revision and records each slot state.

Boot protocol: host persists a fresh `bootId` and `previousGeneration` in local journal; `POST /v2/gateway/boots` under machine row lock with `{bootId,previousGeneration}` CAS allocates monotonically increasing `bootGeneration` and retires previous boot. A retry for the **current** boot returns its generation. A different boot with stale `previousGeneration` returns 409 and must reconcile local process journal before asking for a new generation. `GatewayHeartbeat={bootId:Id,bootGeneration:string,sequence:string,observedAt:string,hostVersion:string,appVersion:string|null,telemetry:{cpuLoad1:number,cpuCount:number,memoryAvailableBytes:string,memoryPressure:'normal'|'warn'|'critical',diskAvailableBytes:string,activeJobs:number,configuredMaxJobs:number},inventory:{bmad:WorkflowStatus,superpowers:WorkflowStatus},processes:{attemptId:Id,processInstanceId:Id,fence:string,observation:'running'|'stopped'|'unknown'}[]}`. Sequence resets to `1` per boot. Server retains immutable `(machine,bootGeneration,sequence,bodyHash,response)` receipts **durably without TTL**, matching phase02's permanent idempotency replay. **Lookup exact receipt first**: matching hash returns historical 200 response without changing current boot/status, even if that boot is now retired; conflicting hash 409. A **new** request from a retired boot returns `BOOT_RETIRED` 409, even with a larger sequence. Current boot's new sequence must be strictly greater than latest. `receivedAt` is server time, `observedAt` advisory. Heartbeat never writes `gateway_applied`, attempts or guard.

Install report protocol: `InstallReport={reportId:Id,bootId:Id,bootGeneration:string,configRevision:number,reportedAt:string,results:{bmad:WorkflowStatus,superpowers:WorkflowStatus}}`. Host durably records `reportId` and canonical body before POST. **Under one machine-row/config transaction**, server checks a committed `reportId`/body-hash first and replays its immutable original response with **no** applied/status mutation, even if its boot/config is now retired. For a **new** report ID it then requires `(bootId,bootGeneration)` equal the current nonretired boot **before** any report/status/applied write; stale boot returns `BOOT_RETIRED` 409. Next compare current desired revision and exact source identity (`name/version/sourceRevision/payloadSha256/sourceTreeSha256/sourceManifestSha256/packageIntegrity`) plus every non-null desired projection's `runtime/sourceTreeSha256/manifestSha256/treeSha256/derivation`. Only both source slots and all declared projection slots `current` with exact hashes advance `gateway_applied.revision`; partial/error/mismatch preserves previous applied revision and records latest per-slot status. A new stale-config report returns `CONFIG_REVISION_CONFLICT`; an already committed identical report replays its response after config change without mutation. Host may report `installing`; UI reads each source/runtime slot. `appliedConfigRevision` is server-derived, never accepted from heartbeat.

`007_gateway.sql` owns `gateway_configs(machine_id PK FK machines,revision integer,desired jsonb,max_jobs integer,enabled boolean,updated_at)`, `gateway_applied(machine_id PK FK machines,revision integer,inventory jsonb,workflow_status jsonb,applied_at)`, `gateway_boots(machine_id FK machines,boot_id uuid,boot_generation bigint,previous_generation bigint,retired_at timestamptz NULL,PRIMARY KEY(machine_id,boot_id),UNIQUE(machine_id,boot_generation))`, `gateway_heartbeats(machine_id PK FK machines,boot_id uuid,boot_generation bigint,sequence bigint,received_at,telemetry jsonb,host_version text,app_version text NULL)`, `gateway_heartbeat_receipts(machine_id,boot_generation,sequence,body_hash char(64),response jsonb,received_at,PRIMARY KEY(machine_id,boot_generation,sequence))`, `gateway_install_reports(id uuid PK,machine_id FK machines,boot_generation bigint,config_revision integer,body_hash char(64),report jsonb,response jsonb,received_at)`, `gateway_attempt_projections(attempt_id uuid PK FK attempts,machine_id uuid FK machines,install_report_id uuid FK gateway_install_reports,fence bigint,process_instance_id text,source_tree_sha256 char(64),runtime text CHECK IN('claude','codex','api'),projection_manifest_sha256 char(64),projection_tree_sha256 char(64),created_at)`, `gateway_commands(id uuid PK,machine_id FK machines,type CHECK IN('sync_workflows','probe','reconcile_host'),payload jsonb,state CHECK IN('queued','received','completed'),result jsonb NULL,created_at,received_at NULL,completed_at NULL,cursor bigint UNIQUE)`, plus `gateway_command_cursor(singleton boolean PK CHECK(singleton),value bigint)` initialized zero. Retired boot and receipt rows remain durable like phase02 idempotency. Same machine row lock serializes boot, heartbeat, config and install report CAS. Projection row insert checks attempt machine/fence/process identity, accepted install report pair and `toDomainPin(source)` in transaction; single immutable row per attempt. Child exits without side effects if gate/parent channel closes before release. `ProcessJournal.observe(record):Promise<'running'|'stopped'|'unknown'>` and `markStopped` require verified OS exit/wait of exact launch identity; missing proof is `unknown`, never `not_started` or `stopped` inferred from missing parent record. Unknown retains guard and blocks replacement. `DispatchCapacity.sampleAndDecide(request:{kind:'implement'|'review'|'fix',ticketId,ownershipKeys:string[],maxJobs:number}):Promise<{allowed:boolean,telemetry:Telemetry,reason:string,checkedAt:string}>`; phase06 invokes it before every dispatch and persists rationale/server decision. Phase03 exposes it, not an alternate claim permit.

`HttpOperationJournal.prepare(input:{operationId:Id,method:'POST'|'PUT',route:string,phase:string,canonicalBody:unknown}):Promise<{idempotencyKey:string,bodyHash:string}>` assigns a **unique key per logical mutation and phase**, stores exact canonical body/hash/route/key and fsyncs before network write. `recordResponse(operationId,status,body)` is durable. On lost reply/restart, `replay(operationId)` sends the identical route/body/key; it never generates a new key for that operation. Boot handshake, heartbeat, claim, checkpoint, reconcile, result, finalize and gateway ACK/install report each have distinct operations; Phase02 `finalize` always gets a new key distinct from `result`. Retain host operation records for unresolved operations indefinitely; completed heartbeat records may be compacted locally after server acknowledgement because the immutable server receipt remains. After replay or ambiguous response, query server attempt/command before any launcher release or later side effect. No secrets in operation body/log.

`ResourceRegistry.reserveOwnedPath(input:{runId:Id,kind:'scratch'|'fixture'|'temp_upload'|'cache'}):Promise<{resourceId:Id,path:string}>` persists a unique name under a private host-only root (`0700`) **before** creation. `createAndAttest(resourceId,create):Promise<{device:string,inode:string,ownerUid:number,kind:string}>` creates exclusively/no-follow under a directory handle, fsyncs metadata and records identity; crash between reserve/create leaves a reservation, not proof of ownership. `registerProcess(runId,processInstanceId,startIdentity)` records launcher ownership separately. `retain(id,reason):Promise<void>` records artifact/dirty/reference reasons; `cleanup(runId):Promise<{deleted:Id[],retained:Id[],failed:Id[]}>` is idempotent only after verified process stop. Cleanup reopens parent dir handles, checks device/inode/UID/type/link count and run reference, atomically renames the same object into host-only quarantine, rechecks identity there, then deletes using no-follow traversal; any mismatch, alias/hardlink or missing proof is retained for manual review. Never recursive-delete by an untrusted stale path. `GatewayStatus` exposes boot ID/generation, server connection, desired/applied revisions, per-workflow `WorkflowStatus` with runtime slots, active/uncertain processes and last telemetry time, never token or raw credential.


## Task 5: Offline sync, command ACK, ticket fence bridge

**Files:** unit 5. **Consumes:** host journal/launcher/HTTP operations/registry, phase02 ticket execution API, gateway routes. **Produces:** `GatewaySync.reconcile():Promise<void>` and `TicketCommandBridge.handle(command):Promise<void>`; no model launch until phase04 adapter and phase06 permit exist. `GatewaySync` is producer of immutable `InstallReport` for server Task3 and durable ACK operations for `gateway_commands`; `TicketCommandBridge` is consumer of Phase02 command/claim/fence and producer of checkpoint/result/reconcile/finalize operations.

- [ ] RED `test/sync.test.ts`: server queues `sync_workflows` while host offline; reconnect fetches desired first, ACKs `received`, installs both source pins and declared Claude/Codex/API projections side by side, reports exact applied revision, then ACKs `completed`.
