# Workflow chính thức của Trợ lý và run graph phase06/T3

## Mục đích

Gắn định nghĩa workflow với đúng source và projection bất biến trước khi tạo run. Gateway trả định nghĩa cho Superpowers và BMAD cùng một digest customization chung, và có bộ kiểm tra byte artifact BMAD. BMAD là định nghĩa hai tầng: tầng định nghĩa đến từ registry, render receipt được latch sau ở server. Server dựng run graph từ definition mà máy dự án đã báo trong install report, qua port điều phối thật. Server mở gate khi artifact thật đã được xác minh, hỏi chủ dự án qua câu hỏi gắn đúng gate và chỉ cho gate tiến khi có câu trả lời chính xác của owner. Gateway có executor chạy renderer BMAD chính thức một lần qua thao tác owned chế độ cây tiến trình (`executeTree`), ghim Python bằng `UV_PYTHON` theo install report và dựng render receipt; đăng ký receipt lên server chưa có; production chưa inject port, resolver hay route trả lời nên mọi lời gọi vẫn bị từ chối.

## Điểm vào

- `gateway/src/assistant/workflow-manifest.ts` → `createWorkflowManifest(registry).loadDefinition(source, projection)` trả `WorkflowDefinition = {sha256, skills, customizationSha256, render?}`; `customizationContext(source, projection, layers)` là hàm thuần tính digest customization dùng chung.
- `gateway/src/workflows/registry.ts` → `WorkflowRegistry.resolve` kiểm cached source/projection và trả root cùng manifest.
- `gateway/src/assistant/render-artifacts.ts` → factory chụp expectation và kiểm artifact byte được cung cấp, trả loại `artifact-inspection` không có authority; `validateRenderDefinition(definition, fileBytes?)` là hàm thuần áp cùng luật và giới hạn đó lên định nghĩa chưa gắn root.
- `gateway/src/assistant/render-executor.ts` → `createRenderExecutor({operations, journal, prerequisites: {uv, python}, clock, timeoutSeconds?})` trả `render({definition, projectRoot, attemptId, operationId})` → `{receipt}` hoặc `{halt: true, reason, log?}`; `reclaimRenderStage(operations, name, identity)` thu hồi stage render đã chứng minh đóng cùng bản ghi leader. `probeRenderPrerequisites({uvPath, projectionRoot, run?})` đo prerequisites cho install report.
- `gateway/src/assistant/tool-client.ts` → `createToolClient({root, baseUrl, bearer, ...})` trả `{execute(turn, event, options?), close()}`: client máy của `POST /v2/assistant/turns/:id/tools`; `toolOperationId(turnId, providerCallId, sequence)` là hàm thuần dẫn xuất operationId.
- `gateway/test/workflow-manifest.test.ts` → kiểm bytes nguồn/projection, pin, mismatch, digest customization và định nghĩa BMAD hai tầng.
- `server/src/assistant/runs.ts` → `createWorkflowRuns({port, resolver, lookup?})` trả `createRun(tx, proof, {rootTicketId, path, definitionSha256})` và `latchRenderedArtifact(tx, runId, evidenceId)`.
- `server/src/assistant/gates.ts` → `createWorkflowGates({resolver, lookup?})` trả `createOwnerQuestion(tx, proof, proposal)`, `recordGateAnswer(tx, owner, {questionId, expectedRevision, scopeSha256, artifactSha256, answer})` và `answerGate(tx, questionId, decisionId)` (chữ ký đóng băng); `gateScopeSha256`, `questionScopeSha256` là hàm thuần của digest phạm vi.
- `server/src/assistant/workflows.ts` → `createDefinitionLookup()` đọc definition đã chứng minh của một máy; `workflowSteps(path)` là bảng ánh xạ nguồn chính thức → bước/gate.

## Các bước

1. Chụp sâu `SourcePin` và `ProjectionPin`, kể cả `derivation.options`, trước mọi lần chờ. Kiểm hai snapshot và dùng chính chúng cho `WorkflowRegistry.resolve`, so manifest và tính digest. Caller sửa object sau lời gọi không thể đổi identity đã xác thực.
2. Chọn các `skills/*/SKILL.md` từ manifest source chính thức. Mỗi path phải là regular file trong cả source và projection, có cùng SHA-256. Adapter đọc lại bytes ở hai root, kiểm hash thực tế và so toàn bộ manifest source/projection với pin. File được mở với `O_NOFOLLOW | O_NONBLOCK`; `fstat` loại FIFO và file không regular trước khi đọc; FD được đóng trong `finally`.
3. `customizationSha256` là SHA-256 của canonical `{schema: 'crew-v2:workflow-customization:1', workflow, sourceTreeSha256, projectionTreeSha256, layers}`. Superpowers có `layers = {}`: projection đã pin không chứa layer tùy biến nào, và phát biểu đó gắn vào `projectionTreeSha256`, nên đổi projection thì đổi digest; thứ tự key không ảnh hưởng. BMAD có đủ 7 layer path (SHA-256 hoặc `null`) đo từ projection. Hàm kiểm lại pin, từ chối source/projection lệch nhau, layer thừa/thiếu và layer bắt buộc bằng `null`.
4. BMAD chỉ nhận runtime `claude`. Từ manifest projection, adapter chọn mọi file `.md` dưới `.claude/skills/bmad-build/` (kể cả thư mục con, không lấy `bmad-build-auto`), `customize.toml` và `_bmad/scripts/{render_skill,config_utils}.py`. Thiếu `SKILL.md`, `workflow.md`, `customize.toml`, một trong hai script, layer bắt buộc `_bmad/config.toml`, hoặc gặp symlink/không phải file ở cây skill hay layer path đều trả `WORKFLOW_SKILL_MISMATCH`. Script không phải file thường cũng trả `WORKFLOW_SKILL_MISMATCH`. Trước khi đọc bytes, adapter gọi `validateRenderDefinition` với kích thước khai trong manifest: quá 128 file được chọn, tên `.md` dài hơn 512 ký tự hoặc chưa chuẩn hóa, source tree khác cây BMAD đã chấp nhận, file trên 16 MiB hoặc tổng trên 32 MiB đều bị từ chối bằng mã của bộ kiểm tra (`RENDER_ARTIFACT_MISMATCH`/`RENDER_ARTIFACT_TOO_LARGE`), nên adapter không trả định nghĩa mà bộ kiểm tra luôn từ chối. Mọi file được chọn và mọi layer có mặt được đọc lại bytes thật trong projection root; kích thước thật phải bằng kích thước đã pin. `skills` là các `.md` được chọn trừ `SKILL.md`. `render = {source, projection, selectedProjectionSha256, layers}` đúng bằng expectation của bộ kiểm tra artifact khi bỏ `projectRoot`/`generationRoot` do host gắn sau.
5. `sha256` của định nghĩa là SHA-256 của canonical `{source, projection, skills, customizationSha256, render}` (Superpowers: `render = null`). Identity này chỉ chứng minh định nghĩa manifest đã đọc; nó không cấp quyền chạy model, phát lệnh hay chứng nhận runtime isolation. Adapter không chạy renderer, `uv` hay process con nào.
6. Bộ kiểm tra artifact nhận byte manifest, projected sources, config layers và output. Nó từ chối proxy/accessor trước khi đọc, giới hạn tổng byte trước copy và kiểm hai quan sát của cùng `customize.toml` nhất quán. Path identity phải là Unicode hợp lệ; manifest schema1 và generation identity khớp canonical JSON của renderer Python. `resolved_values` chỉ nhận key từ token source đã chụp và loại scalar/string-list/review-layer chính thức của exact BMAD tree được chấp nhận. Unknown pin/category, key thừa hoặc short token mơ hồ đều bị từ chối.
7. Adapter không còn trả `RENDER_ARTIFACT_REQUIRED`. Việc từ chối BMAD chưa có artifact thuộc server: run BMAD được tạo với `rendered_artifact_id = null` và admission từ chối dispatch khi giá trị này còn `null`. Không dùng hash/path do client khai báo làm bằng chứng renderer.
   - Executor render BMAD chạy trên máy B. Định nghĩa không có `render` (Superpowers) trả `RENDER_NOT_BMAD` mà không đặt chỗ hay spawn gì. Trước mọi effect, executor kiểm `attemptId`/`operationId` là UUID chữ thường, `projectRoot`, `path`/`realpath` của `uv` và của Python là path tuyệt đối đã chuẩn hóa, sha256 là hex 64 ký tự, version là ASCII in được 1–128 ký tự, không có ký tự điều khiển, `"` hay `\`, tên thư mục project là ASCII in được (`RENDER_REQUEST_INVALID`). Nó chụp định nghĩa, chạy `validateRenderDefinition`, tính lại `customizationSha256` và `sha256` theo đúng công thức của adapter (`RENDER_DEFINITION_MISMATCH`). `projectRoot` phải là thư mục thật và bằng `realpath` của chính nó (`RENDER_PROJECT_ROOT_MISMATCH`). Closure quanh renderer phải đúng projection: `_bmad/scripts/` chỉ có `render_skill.py` và `config_utils.py` (script đứng đầu `sys.path`, nên module thừa như `json.py` hay `__pycache__` sẽ chạy thay stdlib), `_bmad/` chỉ có `scripts`, `render`, `custom` và các layer config đã khai, `_bmad/custom/` chỉ có layer đã khai, thư mục skill đúng tập file được chọn; symlink hay file đặc biệt ở các chỗ này đều bị từ chối. Mọi file được chọn và 7 layer được đọc trong `projectRoot` không theo symlink ở bất kỳ cấp nào (file thường, một link, có giới hạn byte) và phải khớp hash của định nghĩa, layer vắng phải vẫn vắng (`RENDER_INPUT_MISMATCH`). `uv` và Python được resolve `realpath` (chấp nhận symlink kiểu Homebrew); kết quả phải bằng `realpath` mà install report đã ghi và file thật ≤256 MiB phải khớp SHA-256 đã ghi (`RENDER_UV_UNAVAILABLE`, `RENDER_PYTHON_UNAVAILABLE`); chính file `uv` đó được chạy, còn file Python đó được ghim qua `UV_PYTHON`. `witness.uvPath` giữ path đã ghi, `argv[0]` là path đã resolve. Phiên bản `uv`/Python chỉ chuyển tiếp từ install report, không đo lại. `argv[0]` không tự chứng minh điều gì; bằng chứng về `uv` là `uvSha256`, đo trên chính file đã được thực thi, nên server không được coi `argv[0]` là bằng chứng. Các bước này không spawn gì.
   - Executor chạy đúng một lần argv chính thức `uv run --no-cache {root}/_bmad/scripts/render_skill.py --project-root {root} --skill {root}/.claude/skills/bmad-build` qua `OwnedOperations.executeTree` trên stage riêng `stages/render-{operationId}`: `uv` luôn chạy Python như process con, nên chỉ chế độ cây tiến trình (session riêng, phải rỗng khi leader thoát) mới cho receipt được. Owned root phải canonical (`realpath`) để profile sandbox khớp path của stage, nếu không thì `RENDER_OPERATION_UNAVAILABLE`. `journal.blocked()` báo còn stage render chưa đối soát thì trả `RENDER_RECONCILE_REQUIRED` trước mọi thao tác. Receipt `receipts/render-{op}.json`, bản ghi leader `receipts/render-{op}.leader` hay stage đã tồn tại (helper thoát 22) thì trả `RENDER_OPERATION_REUSED`, không chạy lại; owned root đang bị thao tác khác khóa (helper thoát 20) thì trả `RENDER_OPERATION_BUSY`; guard `.operations.guard` không phải file riêng hợp lệ (thoát 24) thì trả `RENDER_OPERATION_GUARD_INVALID`. Mỗi bước được ghi bền qua `journal.record(operationId, {state, stageIdentity, leader, receipt, error})`: `reserved` trước khi tạo stage, `pending` khi stage có, `complete` khi vòng đời con đã chứng minh (hoặc con chưa từng chạy), `unknown` khi không, `deleted` khi stage đã thu hồi; ghi lỗi trước khi spawn thì thu hồi stage và trả `RENDER_OPERATION_UNAVAILABLE`. Thao tác owned cấp env riêng (HOME/XDG/TMPDIR trong stage, `PATH=/usr/bin:/bin`), giới hạn thời gian (mặc định 60 s, tối đa 120 s), giới hạn ghi và theo dõi process; executor thêm `UV_OFFLINE=1`, `UV_NO_CONFIG=1`, `UV_PYTHON_DOWNLOADS=never`, `UV_PYTHON={realpath Python}`, `PYTHONDONTWRITEBYTECODE=1` (env, không đổi argv) và profile `sandbox-exec` cấm mọi network, chỉ cho ghi vào stage và `{root}/_bmad/render`. `EXECUTOR_BUSY` hay `EXECUTOR_GUARD_INVALID` từ `executeTree` nghĩa là helper từ chối trước khi fork, nên stage được thu hồi ngay (bản ghi `complete` không receipt rồi `deleted`) và trả `RENDER_OPERATION_BUSY`/`RENDER_OPERATION_GUARD_INVALID`. Thao tác báo không chứng minh được vòng đời con trả `RENDER_LIFETIME_UNKNOWN`; helper lỗi khác trả `RENDER_OPERATION_UNAVAILABLE`; hai trường hợp này ghi `unknown` kèm nội dung `.leader`, giữ stage và bản ghi leader lại để đối soát. Timeout ở chế độ cây chỉ có receipt khi helper đã chứng minh session rỗng, nên stage được thu hồi như HALT thường. Hết giờ trả `RENDER_TIMED_OUT`, exit 127 trả `RENDER_UV_UNAVAILABLE`, exit khác 0 trả `RENDER_EXIT_NONZERO`.
   - Install report đo prerequisites bằng `probeRenderPrerequisites` trong môi trường owner (không shell; env của owner cộng `UV_OFFLINE=1`, `UV_PYTHON_DOWNLOADS=never`; mỗi lệnh ≤10 s, stdout ≤64 KiB): `realpath` và SHA-256 (≤256 MiB) của `uv`, `uv --version`, rồi `uv python find --script {projectionRoot}/_bmad/scripts/render_skill.py` để lấy đúng interpreter mà `uv run` của runtime sẽ chọn, `realpath`/SHA-256 của nó và `-c 'import sys;print(sys.version.split()[0])'`. Output phải là một dòng ASCII in được, path tuyệt đối đã chuẩn hóa (`RENDER_PREREQUISITE_INVALID`); phiên bản phải là CPython 3.11 trở lên vì renderer cần `tomllib` (`RENDER_PYTHON_UNSUPPORTED`); lệnh hay file lỗi trả `RENDER_UV_UNAVAILABLE`/`RENDER_PYTHON_UNAVAILABLE`. Executor dùng đúng bộ `{path, realpath, sha256, version}` này.
   - Output gộp stdout/stderr (≤64 KiB) phải đúng một dòng `read and follow {G}/workflow.md`, với `G = {root}/_bmad/render/bmad-build/{slug}-{sha256(root)[:12]}/{20 hex}` và `{G}/workflow.md` là file thường (`RENDER_STDOUT_MISMATCH`). Thư mục generation chỉ được chứa `manifest.json` và đúng các output tên theo source `.md` (không symlink, không file thừa). Trước lần kiểm closure đầu, executor tạo `{root}/_bmad/render` nếu chưa có rồi ghi lại `dev/ino/mtime/ctime` (ns) và kích thước của project root, `.claude`, `.claude/skills`, `_bmad`, `_bmad/scripts`, `_bmad/custom` (hoặc việc nó vắng), từng file nằm trực tiếp trong ba thư mục `_bmad` đó, và mọi thư mục cùng file trong cây skill. Closure được kiểm lại sau khi chạy và các giá trị này phải không đổi, nên file được thêm rồi xóa, hay file bị ghi đè rồi trả lại đúng bytes cũ giữa hai lần kiểm, cũng bị bắt (`RENDER_ARTIFACT_MISMATCH`). Executor đọc lại input sau khi chạy rồi đưa cả bộ bytes cho bộ kiểm tra artifact; lệch bất kỳ, kể cả generation khác hash thật hay layer đổi trong lúc render, trả `RENDER_ARTIFACT_MISMATCH`. Executor không bao giờ ghi vào generation, nên lần render thứ hai gặp generation byte-identical để renderer chính thức tự kiểm và giữ nguyên. Mọi HALT sau khi đã có `execution.log` trả kèm `log = {sha256, firstLine, lastLine}`: digest của toàn bộ log và dòng không rỗng đầu tiên, cuối cùng đã làm sạch. Dòng cuối lấy từ 4 KiB cuối của log; nếu cửa sổ này không bắt đầu ở đầu file thì phần dòng dở đầu cửa sổ bị bỏ, nên dòng cuối dài hơn cửa sổ trả rỗng thay vì một mảnh giữa dòng. Cách làm sạch: path đã biết thành nhãn như `{project-root}`, `{uv}`, `{python}`, chỉ giữ phần đuôi gồm ký tự path thường (`A-Za-z0-9._/-`), nên `?token=…` sau path vẫn qua luật credential; `Bearer …` và giá trị của trường có tên chứa `token`, `secret`, `password`/`passwd`, `credential`, hoặc `key` là một từ riêng (`api_key`, `ACCESS_KEY`, `key`) hay hậu tố camel-case (`apiKey`) dạng `name: value` hay `name=value`, cùng mọi `NAME=value`, bị thay bằng `{redacted}`, còn `KeyError`, `keyword` giữ nguyên; mọi path `/…` hay `~/…` khác thành `{path}` bất kể ký tự đứng trước, kể cả backtick hay ngoặc; chỉ ASCII in được, ≤256 ký tự; vẫn là text không tin cậy), tính trước khi stage bị thu hồi. Stage chỉ bị thu hồi khi thao tác owned đã chứng minh process con đóng; thu hồi xóa stage rồi xóa `receipts/render-{op}.leader` (file thường, một link, cùng uid), còn `render-{op}.json` giữ lại làm bằng chứng operation đã chạy; thu hồi lỗi trả `RENDER_CLEANUP_FAILED`. Thành công trả `{kind: 'workflow_render_receipt', attemptId, data: {definitionSha256, customizationSha256, projectRoot, generationPath, inspection, witness: {uvPath, uvSha256, uvVersion, python: {path, sha256, version}, argv, exitCode, stdoutPath, startedAt, endedAt, operationId}}}`; `witness.python` là nhân chứng, không thuộc identity của generation (renderer không băm phiên bản Python); `witness.argv` là argv `uv` chính thức, không gồm lớp `env`/`sandbox-exec`. Executor không gọi server; receipt chỉ là object để lát đăng ký gửi đi.
8. `createRun` kiểm input, khóa root (phải là request) rồi project, rồi mới gọi resolver Actor persisted (turn chưa admit 503, admission lệch 403, không ghi row). Actor luôn là máy Trợ lý A do resolver trả, không lấy từ caller.
9. Definition tra theo máy B đang gắn với project. Lookup chỉ đọc `gateway_applied.workflow_status` của máy đó: slot projection và slot source phải `current`, digest phải tính lại đúng trên pin của slot, skills, customization và render. Không suy definition từ applied revision. BMAD chỉ có ở runtime `claude` và luôn có `render`; Superpowers không có `render`. Hash không có, slot không current, digest lệch hoặc chỉ máy khác báo đều trả 422 `WORKFLOW_DEFINITION_UNKNOWN`. Definition khác workflow của path trả 422 `WORKFLOW_PATH_MISMATCH`; nguồn của một bước không có trong definition trả 422 `WORKFLOW_SKILL_MISSING`. Pin hoặc `workflowChoice` của root khác workflow trả 409; root đã có run trả 409 `WORKFLOW_RUN_EXISTS`.
10. Graph là bảng ánh xạ cố định từ nguồn đã pin (bảng bên dưới). Mỗi bước là một ticket `step` con của root với `stepOperationId` cấp trước. Criteria của ticket ghi `workflowRun = {runId, path, stepKey, stepOperationId, sourcePath, citation, gates:[{id, kind, requiredActor, trigger, citation}]}`. `trigger` là `on_stage` (run nào cũng qua) hoặc `after_three_failed_fixes` (gate `architecture_discussion`, chỉ materialize sau ba lần sửa hỏng). Bước execution của architectural còn có `executionChoices` (skill, source path, SHA của từng lựa chọn) và `resolvedByGateId` = gate kế hoạch; bước này chưa dispatch được khi gate chưa chọn. UUID gate được giữ chỗ trong `workflow_steps.gate_ids`; không tạo `workflow_gates` khi chưa có artifact. Mặc định tuần tự: mỗi bước chỉ chờ bước liền trước.
11. Chạy song song chỉ khi `assistant_config.policy.parallelApprovalId` trỏ tới quyết định `approval` của owner trong cùng root, với `scope.parallel = {rootTicketId, path, definitionSha256, units:[{key,title,ownershipKeys}]}` khớp chính yêu cầu. Quyết định của root khác không phải override cho root này: run chạy tuần tự, `parallel_approval_id` null. Trong cùng root, quyết định không phải `approval` của owner trả 403 `WORKFLOW_PARALLEL_APPROVAL_INVALID`. Khi hợp lệ, bước triển khai tách thành từng phần với `stepOperationId` và ownership riêng, cùng chờ bước trước; bước review chờ đủ mọi phần.
12. Mọi ID của run (run, step, `stepOperationId`, gate, khóa cạnh) được dẫn xuất từ `operationId` của proof, nên graph là hàm thuần của operation, input và các row đã đọc. `runs.createRunRequest(tx, operationId, input)` trả đúng request `{action:'create_run', payload:{rootTicketId, path, definitionSha256, graphSha256}}` mà transport băm vào `request_hash`. `createRun` dựng lại graph, rồi trong một savepoint nội bộ gọi `port.authorizeGraph(sp, actor, proof, input, graph)` một lần; port tự tính lại digest và so `request_hash`. Lỗi bất kỳ sau lần ghi đầu (lỗi JS của port hay lỗi DB) rollback toàn bộ ghi của `createRun` và cả lần dùng operation, transaction của caller vẫn dùng được. Trong savepoint: insert `workflow_runs` (revision 1, `rendered_artifact_id` null). Mỗi ticket con đi qua session của port; sau khi ticket và step tồn tại thì ghi `assistant_operation_ids` (`action_kind='create_ticket'`, `target_identity` = ticket ID). Mỗi cạnh dependency cũng đi qua session rồi ghi operation riêng (`target_identity = ticketId:predecessorId`). `precondition_sha256` là hash của graph; `effect_id = sha256(canonicalJson([runId, stepOperationId, actionKind, targetIdentity, preconditionSha256]))`, cùng công thức `deriveEffectId` của gateway. Session phải được `close` với mọi phần tử đã dùng.
13. `latchRenderedArtifact` chỉ cho run `bmad-*` chưa latch (409 `WORKFLOW_RENDER_NOT_REQUIRED` / `WORKFLOW_RENDER_ALREADY_LATCHED`). Evidence phải là `workflow_render_receipt` có attempt. Lệch bất kỳ điều nào trả 409 `WORKFLOW_RENDER_RECEIPT_INVALID`. Đúng thì set `rendered_artifact_id` và tăng revision trong cùng một câu UPDATE có điều kiện. Server chưa có bản ghi workspace nên chưa đối chiếu được `projectRoot` với workspace thật; việc đó thuộc lát đăng ký receipt trên máy B.

14. `createOwnerQuestion` là tool `ask_owner` của Trợ lý. Câu hỏi phải gắn một ticket (thiếu thì 422 `WORKFLOW_QUESTION_TICKET_REQUIRED`). Thứ tự khóa root → project → resolver Actor persisted, rồi scope của proof phải đúng root và có tool `ask_owner` (thiếu thì 403 `ORCHESTRATION_ACTION_NOT_IN_SCOPE`). Row operation pending phải được ghi trong chính Tx, cùng turn và snapshot của scope, với `request_hash = operationRequestSha256({action:'ask_owner', payload: proposal})` trên đúng proposal đã gửi; lệch thì 403 `ORCHESTRATION_REQUEST_MISMATCH`, row từ Tx trước thì 404. ID câu hỏi dẫn xuất từ `operationId`, nên một operation chỉ hỏi được một lần (lần hai 409 `ASSISTANT_OPERATION_CONSUMED`). `conversationId` phải là hội thoại của turn đang hỏi.
15. Câu hỏi gắn gate chỉ hợp lệ khi gate ID nằm trong `workflow_steps.gate_ids` của bước, ticket là ticket của bước, và stage trong criteria khớp bảng nguồn đã pin cùng row bước bất biến (source, skill, số gate, kind); lệch trả 409 `WORKFLOW_GATE_UNKNOWN`. Thiếu `artifactSha256` trả 409 `WORKFLOW_ARTIFACT_REQUIRED`. Artifact được coi là đã xác minh khi có evidence `artifact` trên chính ticket bước với đúng `data.sha256`, do attempt của máy và `binding_revision` hiện hành của project ghi; nếu không thì 409 `WORKFLOW_ARTIFACT_UNVERIFIED`. Chỉ artifact mới nhất của bước (theo `fence` của attempt, rồi `created_at` của evidence; cùng mốc thì mọi row phải cùng SHA) được hỏi hoặc duyệt; bytes cũ hơn trả 409 `WORKFLOW_ARTIFACT_SUPERSEDED`. Mỗi gate có đúng một artifact hiện hành; bước sinh nhiều file phải gói chúng thành một artifact. Run có run mới hơn trên cùng root (theo thứ tự journal `ticket.created` của ticket bước, đọc qua index `events(project_id, cursor)`) trả 409 `WORKFLOW_RUN_SUPERSEDED` khi hỏi hoặc trả lời; nếu run này hoặc một run khác của root không có event `ticket.created` thì thứ tự không xác định và cũng trả 409 (đóng an toàn). Definition của run phải còn đúng thứ máy dự án đang chứng minh (cùng source, projection, customization), nếu không thì 409 `WORKFLOW_DEFINITION_STALE`. Run BMAD chưa latch render trả 409 `WORKFLOW_RENDER_REQUIRED`. Gate `on_stage` không nhận `cycleId` (400). Gate `after_three_failed_fixes` chỉ mở khi run có ít nhất ba kết quả review `initial_review`/`repair_review` thất bại và `cycleId` là một trong các cycle đó; review hạ tầng hoặc review đạt không tính (409 `WORKFLOW_GATE_NOT_TRIGGERED`).
16. Digest phạm vi do server tự tính: gate là `sha256(canonicalJson(['crew-v2:workflow-gate-scope:1', {rootTicketId, runId, stepId, gateId, kind, requiredActor, trigger, sourcePath, sourceSha256, artifactSha256, cycleId, definitionSha256, customizationSha256, renderedArtifactId}]))`; câu hỏi không gate là `['crew-v2:owner-question-scope:1', {conversationId, rootTicketId, ticketId, runId, stepId}]`. `scopeSha256` của proposal khác giá trị này trả 409 `WORKFLOW_QUESTION_SCOPE_MISMATCH`. Lần hỏi đầu materialize row `workflow_gates` bất biến (`pending`, `decision_id` null) rồi mới tạo câu hỏi revision 1. Câu hỏi mới cho cùng gate đánh dấu câu đang mở là `superseded` và lấy revision kế tiếp. Gate đã ghim artifact khác trả 409 `WORKFLOW_GATE_ARTIFACT_MISMATCH`: artifact mới cần run mới thay run cũ. Gate đã quyết định trả 409 `WORKFLOW_GATE_DECIDED`, nên duyệt đã có hiệu lực không bị hỏi lại. Câu hỏi không gate không mang artifact hay cycle.
17. `recordGateAnswer` chỉ nhận Actor owner; máy, kể cả Trợ lý, trả 403 `OWNER_REQUIRED` trước mọi truy vấn. Hàm tự khóa `event_cursor` trước (cùng thứ tự với `mutate()`, vì decision ghi event), rồi root → project → ticket câu hỏi → gate → câu hỏi; precondition cho caller (route sau này): không giữ các khóa đó theo thứ tự khác. Câu hỏi đã trả lời trả 409 `WORKFLOW_QUESTION_ANSWERED`; câu bị thay hoặc `expectedRevision` lệch trả 409 `WORKFLOW_QUESTION_STALE`; `scopeSha256` lệch trả 409 `WORKFLOW_QUESTION_SCOPE_MISMATCH`; `artifactSha256` lệch trả 409 `WORKFLOW_GATE_ARTIFACT_MISMATCH`. `answer = {verdict, option, executionMethod, parallel, text}`: câu hỏi gate nhận `approve`/`reject`, câu hỏi không gate nhận `answer`; `option` là `null` hoặc một lựa chọn của câu hỏi. Chỉ gate giải quyết bước execution (gate kế hoạch của architectural) nhận `executionMethod` và `parallel`. Khi duyệt, `executionMethod` phải là một `method` của `executionChoices`, và mỗi lựa chọn trong criteria phải khớp bảng nguồn lẫn SHA của definition hiện hành (409 `WORKFLOW_EXECUTION_CHOICE_INVALID`). `parallel = {units:[{key,title,ownershipKeys,dependsOn?}], sharedInputSha256}` chỉ được chấp nhận sau kế hoạch viết và cần hash input dùng chung. `units` theo luật chung `parallelUnits` (cũng áp cho duyệt song song của run `bounded`): 2–16 phần, key/title hợp lệ, không field lạ, ownership key là path tương đối hợp lệ theo `validPath` của server docs (bỏ segment `./` và một `/` cuối; `..`, path tuyệt đối, `//`, dấu `\` bị từ chối). Khi so xung đột, key được so theo `decodeURIComponent(path).normalize('NFC').toLowerCase()` vì FS dự án có thể không phân biệt hoa thường hay dạng Unicode; giá trị lưu giữ nguyên như owner gửi, `dependsOn` chỉ trỏ phần khác. Hai phần sở hữu cùng path hoặc path lồng nhau (thư mục cha/con) trả 409 `WORKFLOW_PARALLEL_OWNERSHIP_CONFLICT`; có phụ thuộc trả 409 `WORKFLOW_PARALLEL_DEPENDENCY`. Lỗi shape trả 400 ở gate, 409 `WORKFLOW_PARALLEL_SCOPE_MISMATCH` ở run. Ở gate khác, `parallel` trả 409 `WORKFLOW_PARALLEL_SCOPE_MISMATCH`. Trong một savepoint, server gọi `recordDecision` với Actor owner: `approval` cho gate, `owner_answer` cho câu hỏi; `scope = {questionId, questionRevision, gateId, runId, stepId, artifactSha256, scopeSha256, verdict}` cộng `executionChoice` và `parallel` khi có. Sau đó server ghi `assistant_answers` bất biến rồi gọi `answerGate`. Lỗi bất kỳ hoàn tác cả decision lẫn answer, còn Tx của caller vẫn dùng được.
18. `answerGate(tx, questionId, decisionId)` khóa và đọc lại toàn bộ. Câu hỏi phải đang mở. Decision phải là của owner với kind đúng (`approval` cho gate owner bắt buộc, `owner_answer` cho câu hỏi); decision của máy, `delegated`, hay sai kind đều trả 403 `WORKFLOW_GATE_DECISION_INVALID`. Phải có row `assistant_answers` của owner cho đúng revision, trỏ tới decision này, nếu không thì 403 `WORKFLOW_ANSWER_REQUIRED`. `scope` của decision phải đúng bằng scope dựng lại từ câu hỏi và nội dung answer. Gate phải còn `pending`, artifact và digest phạm vi tính lại từ các row hiện hành phải khớp, artifact vẫn được máy hiện hành xác minh và còn là artifact mới nhất của bước khi duyệt (bytes đã bị thay chỉ được `reject`). Khi đủ điều kiện, server latch `decision_id`, đặt gate `approved`/`rejected` và câu hỏi `answered`, mỗi việc bằng UPDATE có điều kiện nên chỉ tiến một lần; gọi lại trả 409. Route HTTP `POST /v2/assistant/questions/:id/answers` là controller mỏng, chưa mở trong lát này.

19. `tool-client.ts` là phía máy của route tool (driver, supervisor và model thuộc lát khác). `execute({fence, inputSnapshot}, event)` kiểm `RoutingEvent` theo union tool trước mọi I/O: tên tool lạ, field thừa/thiếu, UUID/digest/counter sai, `providerCallId` ngoài ASCII hiển thị 1–4096 ký tự hoặc có dấu phẩy, event `finished` đều trả `ToolClientError` kind `invalid` và không ghi journal. UUID của fence và `snapshotId` được chuẩn hóa lowercase trước khi dẫn xuất và journal, nên cách viết hoa/thường không tạo xung đột giả. `operationId` là UUID (layout v5) của SHA-256 canonical `['crew-v2:assistant-tool-operation:1', turnId, providerCallId, sequence]`, nên mọi lần chạy lại cùng lời gọi, kể cả sau restart, dùng cùng operationId. Request được ghi vào `HttpOperationJournal` (thư mục riêng `<root>/assistant-tools`, vì mỗi thư mục journal có đúng một writer) TRƯỚC lần gửi đầu. Body journal giữ `call` dạng canonical JSON text (`callJson`) nên phép quét khóa-tên-secret của journal chỉ áp cho phần envelope cố định, không áp cho khóa nghiệp vụ trong ticket/câu hỏi; transport dựng lại đúng body năm field. `providerCallId` nằm trong `phase` đã journal (`assistant-tool:<id>`) và được gửi đúng một lần ở header `x-crew-provider-call-id`, không nằm trong body hay request hash. `bearer` là chuỗi hoặc hàm được gọi ở mỗi lần gửi, nên credential đã làm mới đến ngay lần thử sau; bearer rỗng hoặc chứa ký tự ngoài ASCII hiển thị trả `unauthorized` ngay, không gửi, không retry; bearer không vào journal, lỗi hay log. Hai `execute` đồng thời cùng operation có thể gửi hai request song song (server idempotent, kết quả lưu giống nhau). Cùng operationId với request khác (fence/pin/payload đổi) trả kind `conflict` ngay, không I/O. Journal `assistant-tools` tạo bởi bản đầu (body có `call` trực tiếp, chưa có `callJson`) không tương thích: phải xóa thư mục `<root>/assistant-tools` cũ trước khi mount production.
20. Journal giữ vĩnh viễn phản hồi đầu của một operation, nên chỉ kết quả nghiệp vụ của route được ghi: 200 hợp lệ, hoặc 400/403/404/409/422 mà body mang mã lỗi của route: mọi mã `ASSISTANT_*`, `ORCHESTRATION_*`, `WORKFLOW_*` trên các status đó, cùng danh sách tường minh mã không có prefix (`INVALID_INPUT`, `VALIDATION`, `PATH_INVALID`, `PROVIDER_CALL_ID_INVALID`, `NOT_FOUND`, `IDEMPOTENCY_CONFLICT`, `REVISION_CONFLICT`, `TICKET_CLOSED`, `PROJECT_NOT_BOUND`, `TICKET_HIERARCHY`, các mã dependency/repair/completion của ticket, `DOCS_ENCODING_INVALID`, `SOURCE_UNVERIFIED`...); đó là phán quyết tất định, terminal, không gửi lại, phát lại sau restart không I/O, và kind phân biệt theo status/mã (`invalid`, `forbidden`, `not_found`, `stale`, `budget`, `conflict`, `rejected`). Cùng status mà thiếu hoặc lạ mã (404 mặc định của Fastify, trang lỗi proxy, server cũ chưa có route) là `misconfigured`, không ghi, không retry. Mọi thứ còn lại được ném từ transport và KHÔNG ghi, operation giữ mở để gọi lại với cùng operationId và body: 401 (kind `unauthorized`, `retryable`, không tự thử lại; làm mới credential rồi gọi lại), 408/425/429/5xx kể cả 503 `SERVICE_UNAVAILABLE` và mất mạng/timeout (thử lại có giới hạn, một request thật mỗi lượt, lịch 1s nhân đôi tới 60s, `Retry-After` chỉ kéo dài, không rút ngắn backoff (lấy max) và chặn trần 60s; hết `maxAttempts`, mặc định 6, ghi đè theo lời gọi, trả `unavailable` retryable), 5xx mang mã cấu hình `ASSISTANT_TOOLS_NOT_CONFIGURED`, `ASSISTANT_POLICY_INVALID`, `ASSISTANT_STORE_MISSING`, `ASSISTANT_ADMISSION_NOT_CONFIGURED`, `ORCHESTRATION_COMMAND_NOT_RELEASED` (kind `not_configured`, dừng ngay, giữ operation), 3xx (kind `misconfigured`, không theo redirect, không thử lại), 413 và 4xx không liệt kê (kind `rejected`, không retry). Ánh xạ mã theo route thật: 400 `invalid`; 403 `forbidden`; 404 `not_found` (một hình dạng cho turn không tồn tại, máy khác và fence/turn không còn hiện hành, caller dừng turn); 409 `ASSISTANT_INPUT_STALE` `stale`, `ASSISTANT_TOOL_BUDGET_EXHAUSTED` `budget`, còn lại (`IDEMPOTENCY_CONFLICT`, `ASSISTANT_OPERATION_CONFLICT`, mã workflow) `conflict`; 422 `rejected`. Lỗi mang kind, status và mã server, không mang body.
21. Phản hồi 200 phải đúng envelope `{operationId, state, result, errorCode}` với operationId khớp, được kiểm trước khi ghi (phản hồi sai không bị ghi và kind là `response_invalid`). `completed` chỉ nhận đúng một kind giá trị theo tool (`read_catalog`→`catalog` có `truncated`, `read_docs`→`docs`, `route_message`→`route`, `read_execution_candidates`→`execution_candidates`, `assess_ticket`→`assessment`, `ask_owner`→`question`, `create_run`→`run`, `request_dispatch`→`dispatch`, `request_review`→`review`, `publish_reply`→`reply`) và đúng tập field của kind; `pending` và `rejected` không mang giá trị, `rejected` có `errorCode` (ví dụ `TOOL_NOT_RELEASED`). `pending` được trả nguyên, chờ GET `/v2/assistant/turns/:id/tools/:operationId` (chưa có; server hiện không phát sinh `pending`). Quy tắc cho tác giả server: mã transient (hết thời gian khóa, serialization, quá tải) phải dùng 5xx; một 4xx trong namespace `ASSISTANT_`/`ORCHESTRATION_`/`WORKFLOW_` được coi là phán quyết tất định và sẽ được ghi vào journal vĩnh viễn. Test `every server error code of the tool path` quét `new ApiError('CODE', status)` trong `server/src/{assistant,tickets,docs}` và fail khi một cặp mới chưa được client phân loại. Chưa có: ghi fsync kết quả rồi `driver.resolve`, dọn journal khi turn kết thúc và mount production.

## Dữ liệu

`workflow_runs` giữ source/projection/definition/customization/path bất biến; chỉ `rendered_artifact_id` và `revision` đổi được (trigger SQL011). `workflow_steps` và `assistant_operation_ids` bất biến hoàn toàn. Render receipt là `evidence` loại `workflow_render_receipt` với `data = {definitionSha256, customizationSha256, projectRoot, generationPath, inspection, witness}`; executor trên máy B dựng object này; lát đăng ký lên server chưa có. Gate chỉ materialize khi artifact thật đã được xác minh; UUID đặt trước không thay cho `workflow_gates.artifact_sha256` bắt buộc. `workflow_gates` chỉ đổi `decision_id` (latch một lần) và `state`; `assistant_questions` chỉ đổi `state`; `assistant_answers` bất biến và duy nhất theo `(question_id, question_revision)`. Lựa chọn thực thi và duyệt song song nằm trong `scope` của decision owner mà `workflow_gates.decision_id` trỏ tới; T4 phải đọc từ đó, không từ `workflow_steps.skill`/`source_path` của bước execute.

## Flow liên quan

`gateway-workflows` giữ registry và pin source/projection; `server-gateway` lưu install report kèm definition; `server-assistant` giữ scope/TurnFence, resolver và graph authorization của port; `server-tickets` giữ root ticket và owner decisions. Native workflow runtime/admission vẫn cần chứng cứ riêng, không suy ra từ unit fixture này.
